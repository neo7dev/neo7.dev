{{< lead >}}
Containers get `docker-default` whether or not you asked for one. A custom profile
lives on the host rather than in the image, the way to write it is complain mode plus
the denial log rather than guesswork, and the address-and-port network rules in wide
circulation are not valid classic AppArmor.
{{< /lead >}}

<!--more-->

A container is a process with a restricted view of the system. AppArmor narrows
what that process may touch — which paths, which capabilities, which kinds of
socket — enforced by the kernel and independent of whatever the process thinks it
is allowed to do.

On Debian- and SUSE-derived hosts AppArmor is the mandatory access control layer
in use; the RHEL family ships SELinux instead and none of this applies there.

## You are already using one

If AppArmor is enabled on the host, the container runtime applies a profile
called `docker-default` to every container it starts. Check the host first:

```shell
aa-status
```

`docker-default` is generated by the runtime rather than installed as a file, so
it will not be under `/etc/apparmor.d/`. It is a reasonable baseline: it denies
writes to most of `/proc` and `/sys`, blocks mount and ptrace of anything outside
the container, and otherwise gets out of the way.

Two things turn it off, and both are worth knowing because they are easy to do by
accident:

- `--privileged` drops the profile entirely. Not weakened — gone.
- `security_opt: [apparmor:unconfined]` does the same thing explicitly.

Making the default explicit costs nothing and documents the intent:

```yaml
services:
  app:
    image: example/app:latest
    security_opt:
      - no-new-privileges:true
      - apparmor:docker-default
```

`no-new-privileges` is a separate mechanism and belongs there regardless: it
stops the process gaining privileges through setuid binaries, which closes the
most common route out of a narrowed profile.

## A custom profile lives on the host

This is the fact that catches people. An AppArmor profile is **not** part of the
image and cannot be shipped with it. It is a file on the host, loaded into the
kernel, and referenced by name at container start. Move the workload to another
host and the profile does not go with it — it has to be installed there too, by
whatever configuration management put the host together.

The cycle is:

{{% steps %}}

### Write the profile

Put it in `/etc/apparmor.d/`, named after the profile rather than the container.

### Load it into the kernel

```shell
sudo apparmor_parser -r -W /etc/apparmor.d/container-app
```

`-r` replaces an already-loaded profile of the same name, so the same command
works for the first load and every edit after it.

### Reference it by name

```yaml
security_opt:
  - apparmor:container-app
```

The name is the one declared inside the profile, not the filename. They should
match, but the kernel only knows the declared name.

### Recreate the container

`docker compose up -d` is enough. The profile is attached at start; restarting
the runtime does not re-apply it to a running container.

{{% /steps %}}

{{< callout type="error" >}}
If the named profile is not loaded, the container fails to start. That is the
good case — a typo is loud. The bad case is a profile that loads but is
narrower than the workload needs, which fails later, under load, in whatever
code path nobody exercised during testing.
{{< /callout >}}

## Write the profile from observation, not imagination

The guides that tell you to run `aa-genprof` and answer its questions are
describing a host daemon, where the wizard can watch one binary from launch to
exit. A container is a process tree inside its own mount namespace, and the
wizard has no useful view of it.

What works for containers is the same idea taken one step at a time: let it run,
record what it touches, then narrow.

Start from a copy of a permissive profile under a new name, and put it in
**complain mode** — rules are evaluated and violations logged, but nothing is
blocked:

```shell
sudo aa-complain /etc/apparmor.d/container-app
```

Run the workload. Exercise it properly: start it, let it do its job, back it up,
restart it, trigger whatever periodic task it has. Every path you do not exercise
is a path that will be denied in production.

Then read the denials:

```shell
sudo journalctl -k --since "1 hour ago" | grep -i apparmor
```

Each line names the profile, the operation, and the exact path or capability
requested. In complain mode they are logged as `ALLOWED` rather than `DENIED` —
same records, different verdict.

`aa-logprof` turns those records into rule suggestions interactively:

```shell
sudo aa-logprof
```

It is worth running, with the caveat that it suggests the narrowest rule matching
the exact path it saw. Paths containing a PID, a timestamp or a random temporary
name need to be generalised to a glob by hand, or the profile breaks on the next
run.

When the log goes quiet, switch to enforcement:

```shell
sudo aa-enforce /etc/apparmor.d/container-app
```

And then exercise it again. Complain mode logs the first denial of a kind;
enforcement is where you find out what the application does when that access is
actually refused.

## Reading and writing the rules

A minimal profile:

```text
#include <tunables/global>

profile container-app flags=(attach_disconnected) {
  #include <abstractions/base>

  # Read-only configuration
  /etc/app/** r,

  # The data directory, read and write
  /var/lib/app/ rw,
  /var/lib/app/** rw,

  # Nothing else under /mnt, ever
  deny /mnt/** rw,

  network inet stream,
  network inet dgram,
}
```

The parts that cause trouble:

**One star is not two.** `/var/lib/app/*` matches entries directly inside that
directory. `/var/lib/app/**` matches at any depth. A profile written with single
stars works until the application creates its first subdirectory.

**A directory is not its contents.** `/var/lib/app/ rw,` — with the trailing
slash — permits operations on the directory itself. The contents need their own
rule. Both are usually required.

**Permissions are letters and order matters.** `r` read, `w` write, `k` lock, `m`
memory-map executable, `l` link. Execution has its own set: `ix` to run under the
current profile, `Px` to transition to another profile, `Ux` to run unconfined —
which is a hole, not a confinement.

**`deny` beats everything.** A `deny` rule overrides any allow rule, whether it
appears before or after, and whether the allow came from an include. That makes
`deny` the right tool for carving an exception out of a broad abstraction, and
the wrong tool for general policy — a profile that allows little needs no deny
rules at all.

**Includes carry real permissions.** `abstractions/base` grants a long list of
things nearly every program needs. It is also the reason a profile you believed
was minimal can read far more than you intended. Worth reading once.

## The network rule trap

This is where a lot of copied advice is wrong, and the mistake is silent.

Classic AppArmor network rules mediate the _kind_ of socket, not where it goes:

```text
network inet stream,      # IPv4 TCP
network inet dgram,       # IPv4 UDP
network inet6 stream,     # IPv6 TCP
network unix stream,      # local sockets
```

That is the whole vocabulary — address family, socket type, optionally protocol.
There is no classic syntax for "allow TCP to this address on this port".
Rules found in circulation that mix an address and a port into a comma-separated
list alongside `connect`, `bind` and `accept` are not valid classic AppArmor, and
depending on the parser they are either rejected or interpreted as something far
broader than intended.

Finer-grained mediation — matching peer address and port — does exist in recent
AppArmor with kernel support for the extended network rules, but it is a
different syntax and a hard version dependency. Before relying on it:

```shell
apparmor_parser -Q /etc/apparmor.d/container-app && echo "parses"
```

`-Q` parses and loads nothing. If a rule does not parse, you find out before the
profile is live rather than when the container will not start.

{{< callout type="warning" >}}
AppArmor is not where network policy belongs. Which container may reach which
address is a job for network segmentation — separate Docker networks, published
ports only where needed, a firewall at the host. Use AppArmor for the
filesystem and capability surface, which is the part the network layer cannot
see.
{{< /callout >}}

## What this is actually worth

AppArmor does not stop a compromised application from doing what it was designed
to do. It stops it from doing everything _else_ — reading the host's SSH keys
through a bind mount it should never have had, writing into a shared volume that
belongs to another service, loading a kernel module, mapping something executable
out of a writable directory.

That is a narrow benefit and a real one, and it stacks with the cheaper controls
rather than replacing them: run as a non-root user, drop the capabilities you do
not need, set `no-new-privileges`, mount read-only what does not need writing.
A profile is the layer you add after those, when the question is no longer
"could this process escalate" but "how much is reachable if it does".
